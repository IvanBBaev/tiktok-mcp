Privacy Policy

Last updated: 2026-08-29

tiktok-mcp-ai is software you install and run on your own computer. There is no service behind it. The author operates no server, receives no data from you, and has no technical means of observing what you do with it. It is an independent project, not affiliated with, endorsed by, or sponsored by TikTok or ByteDance Ltd.

That makes most of a conventional privacy policy inapplicable, and padding it out with clauses that do not apply would obscure the parts that do. So this document does something narrower and more useful: it states exactly what the software writes to your disk, exactly which hosts it may contact, and the one place where data genuinely leaves your control — the AI client and model you choose to connect it to.

Every statement below is a description of the published source code. Where a claim rests on a specific mechanism, the mechanism is named so you can go and read it.

Who is responsible for what

The software is published by Ivan Baev as an open-source npm package and a public GitHub repository. Publishing is where the author's involvement ends. He is not a party to your use of TikTok, does not host a deployment of this server, and provides no account, login, or backend of any kind.

Two separate things carry the project's name, and it is worth keeping them apart. The first is this documentation website, a static site served from GitHub Pages — see This website. The second is the server itself, which runs as a local, single-user process launched by your MCP client. Everything between here and that section describes the second one.

🔐

There is no controller collecting your data, because there is no collection. The data this software handles moves between your machine and TikTok, plus the AI client you point it at. It never reaches the author.

What the software stores, and where

The server keeps no database. Its entire persistent state is two files in one directory on your machine: an environment file holding credentials, and an append-only publish journal.

The environment file is resolved in this order:

  • TT_ENV_FILE, if you set it, wins outright.
  • On Linux and macOS, $XDG_CONFIG_HOME/tiktok-mcp-ai/.env, falling back to ~/.config/tiktok-mcp-ai/.env.
  • On Windows, %LOCALAPPDATA%\tiktok-mcp-ai\.env. %APPDATA% is deliberately not used: roaming profiles replicate to other machines, and tokens must not roam.

For each configured account, that file holds:

  • the TikTok user access token and the time it expires;
  • the refresh token and the time it expires;
  • the open_id — TikTok's pseudonymous, per-application identifier for the account;
  • the OAuth scopes that were granted.

Alongside them sit your own TikTok application's TT_CLIENT_KEY and TT_CLIENT_SECRET. The client secret is steered into this file rather than into your MCP client's JSON configuration, because that configuration is routinely copied into chat windows and issue reports.

The file is written atomically — a temporary file created with mode 0600, flushed, renamed into place, then re-chmoded — inside a directory created with mode 0700. Concurrent processes serialize their writes through a cross-process lock on that file, so two servers refreshing the same account cannot interleave and lose a rotated refresh token. On Windows there is no POSIX mode to enforce; the protection boundary there is the default access control list of your per-user profile directory, which is documented in docs/SECURITY.md.

Nothing else is persisted. No profile data, no video metadata, no media, no conversation, no history of what was read.

The publish journal

Every attempt to post is recorded in an append-only NDJSON file, journal.ndjson, written beside the environment file with the same 0600 permissions. It exists so that an unattended publish leaves an audit trail you can read, and so the server can refuse to post the same payload twice inside a ten-minute window.

Each attempt writes an intent record containing:

  • a record version, the record type, a unique attempt id, and an ISO-8601 UTC timestamp;
  • the tool name, the profile name and the account's open_id;
  • the single-use plan_id that authorized the write and a digest of the payload;
  • a title_excerpt — the post's title with whitespace collapsed, cut to 48 characters;
  • the media source and the write mode in force.

When the attempt finishes, an outcome record follows with the same attempt id and timestamp, the result, and — depending on the result — TikTok's publish_id, an error code, a failure reason, or the chunk index that failed.

That is the whole schema. The journal records that you posted and what it was called; it never contains the media, the full caption, or any credential. Every string written to it passes through the same redaction primitive described below.

The journal rotates at 5 MB by default (TT_JOURNAL_MAX_BYTES), keeping one previous generation as journal.ndjson.1. It cannot be switched off. If you do not want the history, delete the files — see Deleting your data.

Where data travels

The server enforces a default-deny egress allowlist before any socket is opened. A request whose URL does not satisfy every one of the following is refused with an egress_blocked error rather than sent:

  • the scheme is exactly https:, never upgraded from http;
  • the URL carries no user:password credentials;
  • the port is 443;
  • the host is exactly open.tiktokapis.com for API calls; and for media uploads, exactly open.tiktokapis.com, exactly open-upload.tiktokapis.com, or a regional upload host matching upload.<region>.tiktokapis.com.

Host matching is exact against the URL parser's normalized form, so eviltiktokapis.com and open.tiktokapis.com.attacker.tld are both rejected, and a homograph domain is rejected too. Widening that list is a change to the specification and to this file; it cannot be done through configuration at runtime.

That is the complete set of network destinations. There is no other address anywhere in the code that this server may open a connection to.

Two related flows are worth naming precisely, because in both of them the server is not the party making the request. When you log in, the authorization page at https://www.tiktok.com/v2/auth/authorize/ is opened in your browser; that is your browser talking to TikTok, and TikTok returns the authorization code to a one-shot listener bound to 127.0.0.1 on your own machine. And when you publish with a pull-from-URL source, you hand TikTok a URL and TikTok fetches the bytes; the server never downloads them.

If you run the optional HTTP transport instead of the default stdio one, the server binds a loopback socket and requires a bearer token (TT_HTTP_TOKEN) before it will start. That socket is inbound and local; it changes nothing about where data goes.

What is sent to TikTok

The server is a client for TikTok's official Display API and Content Posting API, so what it sends is what those APIs require: your access token, the field sets you asked for when reading, and the post you asked to publish.

Reading returns your own profile and videos. The available profile fields are open_id, union_id, avatar_url, display_name, bio_description, profile_deep_link, username, is_verified, and the follower_count, following_count, likes_count and video_count statistics — each gated on the OAuth scope that covers it. Video queries return metadata such as title, description, duration, cover and share URLs, embed markup, and view, like, comment and share counts. Default field sets are deliberately minimal; you get more only by asking for it.

Publishing sends the post's title or caption, the privacy level, the interaction and disclosure settings, and the media. In file-upload mode the server reads the file from disk and streams it to TikTok's upload host in chunks; it may only read files beneath the directory you name in TT_MEDIA_ROOT, and if you do not set that variable, reading local files is disabled entirely.

Once data reaches TikTok it is governed by TikTok's own terms and privacy policy, not by this one. The same is true of anything you publish: it is your content on your account.

Your AI client and model

This is the disclosure that matters most, and it is the one a policy of this kind is usually tempted to bury.

An MCP server is only useful because something reads its output. When a tool returns your display name, your bio, your follower counts, or the titles and descriptions of your videos, that result is handed to the MCP client you connected — and the client puts it into the context of whatever model it is driving. Your TikTok data therefore reaches the AI vendor you chose. What happens to it from that point is governed by that vendor's privacy policy and that client's settings, and neither this software nor its author has any control over, or visibility into, it.

Choose that client and model as deliberately as you would choose anything else you grant access to your account. Two mechanisms help you limit the exposure:

  • tool packages — TT_TOOL_PACKAGES, TT_PACKAGES_DENY and TT_PACKAGES_READONLY — let you expose only the tools you actually want the model to have;
  • login scopes are derived from the enabled packages, so a read-only deployment never holds a token carrying posting authority.

Credentials are the deliberate exception to all of this. Tokens never transit an MCP tool in either direction. Authorization happens only in the login command-line flow, and the authentication-status tool reports expiry timestamps and a masked open_id — never a token. A model driving this server cannot read your credentials out of it.

Logs, errors and redaction

The server writes diagnostic logs to stderr — your terminal, or wherever your MCP client routes it. Stdout carries nothing but protocol frames. Logs are not uploaded anywhere; there is no destination they could be uploaded to.

Before anything is serialized to a log line, an error message, a tool result, a plan preview, a journal row or doctor output, it passes through a single redaction primitive that sits below every one of those sinks. It works two ways at once. Structurally it is allowlist-based and default-deny: a field whose name is not on an explicit list has its value replaced with [REDACTED] at every depth, so a newly added secret-bearing field is safe on the day it appears, and the key name itself is scrubbed so a secret used as a key cannot leak. Textually, the exact values of tokens, the client secret and upload tokens are registered and scrubbed out of free text, sensitive query and form parameters are masked by name, Authorization: Bearer headers render as Bearer ***, and a bare URL is reduced to its origin and path so that a credential in a query string cannot survive.

Identifiers that do appear in logs are pseudonymous and truncated: the open_id is TikTok's per-application identifier, not your username, and it is shortened before it is written.

No telemetry

The software collects no analytics, sends no usage reports, counts no installations, checks for no updates, and transmits no crash reports. There is no opt-out because there is nothing to opt out of.

This is a checkable claim rather than a promise. The egress allowlist above admits TikTok's hosts and refuses everything else before a socket is opened, so a phone-home would have to be one of those hosts to work at all; and the package ships with two runtime dependencies, which is a small enough surface to audit yourself.

This website

The documentation site is static HTML, CSS and one JavaScript file, served from GitHub Pages. That script does nothing but enhance the page you are reading: the mobile menu, the back-to-top button, copy buttons, heading anchors, the table of contents and the in-page search. It sets no cookie, writes nothing to local or session storage, and makes no network request of any kind. There is no analytics service, no tag manager and no tracking pixel on any page of this site.

The two legal pages — this one and the Terms of Service — load nothing at all beyond this site's own stylesheet. The documentation home page additionally requests three web fonts from Google Fonts, which means your browser contacts Google's servers when you open it; those requests are subject to Google's policies, not this one.

Because GitHub serves the pages, GitHub's servers necessarily see the requests, and those server logs are GitHub's, handled under GitHub's Privacy Statement. The author has no access to them and has configured no analytics or visitor tracking of any kind.

Deleting your data

Because there is no server, there is nothing to request from anyone. You delete everything yourself:

  • Tokens and credentials — delete the environment file, and any .pre-schema backup sitting next to it. Running tiktok-mcp-ai doctor prints the resolved path if you are not sure where it is.
  • Publish history — delete journal.ndjson and journal.ndjson.1 from the same directory.
  • TikTok's side — revoke this application's access from your TikTok account settings, which invalidates the tokens regardless of what remains on disk.
  • The software — uninstall the npm package.

Data that already reached your AI client or your model vendor is outside all of this; remove it through that vendor's own controls.
